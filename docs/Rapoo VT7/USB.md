# VT7 有线 USB 电量协议

验证日期：2026-10-03，Windows，用户保持 USB 数据线连接。

有线模式使用鼠标本体 `VID_24AE / PID_4613`，仍通过厂商 HID 输入报告被动上报电量。
无需另写一套电量解码器，也不需要发送查询或初始化命令。

## 与接收器模式的比较

| 项目 | 有线 USB | 2.4G 接收器 |
|---|---|---|
| VID:PID | `24AE:4613` | `24AE:1413` |
| 状态集合 | `MI_01 / Col09` | `MI_01 / Col09` |
| usage page / usage | `FF00 / 0002` | `FF00 / 0002` |
| 原生报告长度 | 19 字节 | 19 字节 |
| Report ID | `07` | `07` |
| 电量偏移，含 ID | `[8]` | `[8]` |
| 充电状态偏移，含 ID | `[7]` | `[7]` |
| 实测 `conProtocol = [1] & 0x0F` | `2` | `0` |
| 报告内型号 `[13..14]` | `13 46`，小端 `4613` | `13 46`，小端 `4613` |

USB 枚举实测包含三个接口：`MI_00` 鼠标输入、`MI_01` 键盘/消费者控制/厂商集合、
`MI_02` 厂商升级集合。电量只读取 `MI_01 / Col09`，其他集合不参与电量监控。

## 实机抓包

同时打开两个状态通道，被动监听 25 秒，无输出报告、feature 写入或厂商命令。
本轮有线通道收到 1 条报告，接收器通道收到 0 条。不能据此承诺固定广播周期。

接收时间：Unix 毫秒 `1791012714434`。

```text
07 12 03 4C 04 4C 04 02 64 00 03 01 00 13 46 01 02 02 00
```

- `[1] = 12`：高四位 sensor 为 1，低四位连接模式为 2。
- `[7] = 02`：正在充电。状态码沿用官方定义，不能用“是否插 USB”代替真实充电状态。
- `[8] = 64`：电量 100%。
- `[3..6]`：DPI 1100 × 1100，与接收器报告对应，用于交叉校验；程序界面不显示 DPI。
- `[13..14] = 13 46`：VT7 型号 PID `4613`。
- `[18] = 00`：官方解码器把此字段拆成无线连接标记和 RSSI；与电量校验无关。

HIDAPI 的 Windows native 后端从 Windows preparsed data 重建的状态集合描述符如下。
它是 Windows 已解析集合的重建结果，不宣称是 USB 总线上逐字节读取的原始描述符。
有线与接收器重建结果完全一致：

```text
06 00 FF 09 02 A1 01 85 07 09 02 15 00 26 FF 00 75 08
95 12 81 00 09 02 15 00 26 FF 00 75 08 95 12 91 00 C0
```

`85 07` 定义 Report ID 7；`75 08 / 95 12` 定义 18 个 8 位 payload，
加上报告 ID 后为 19 字节。此集合有 Input 和 Output，没有 Feature。
描述符声明 Output 并不表示读取电量需要发送 Output；本次验证未发送任何设备命令。

## 官方实现交叉验证

2026-10-03 重新下载了 [雷柏官方网页驱动实现](https://hid.rapoo.cn/AHUB_WEB/dist/assets/js/index-BSl-zvvI.js)。
该文件 SHA-256：

```text
E5CBF516BADE682FB3A747A41F4FD7E5F56BBF0B0E5ED05316506297736A2B8F
```

VT7 manifest 使用 `productId: [17939, 5139]`，换算成十六进制就是 `[4613, 1413]`。
两种连接共用 `VT_nrf54L` 驱动以及 usage `FF00:0002` 的状态集合。
官方连接识别以第二个 PID 判断接收器，其余为有线。
Report 7 共用 `Nf` 解码器；WebHID payload 不含 ID，所以电量与状态偏移比原生读取小 1。
`handleReport` 中使用连接模式 0/2 识别无线/有线切换，与实测报告吻合。

此次也纠正原协议文档对 `[18]` 的说明：当前官方 `Nf` 会读取 payload `[17]`，
高位为 `rfConnected`，低 7 位为 `rfRssi`。该字节不是电量校验条件。

## 程序接入与复现

VT7 驱动精确支持 `24AE:1413` 和 `24AE:4613` 的 `FF00:0002` 集合，
其他鼠标 PID 和升级集合仍不匹配。两种连接复用相同纯解码函数。
两者同时存在时先尝试有线；静默超时后仍会轮换检查通道。
轮换期间显示最后真正上报的设备读数和原广播时间，未上报通道不会冒用其他通道的读数。

```powershell
cargo run --locked -- --list
cargo run --locked -- --probe --device rapoo-vt7
cargo run --locked --example capture_vt7 -- 25
```

最后一条命令枚举这两个 PID、重建状态集合描述符并同时被动监听。
原始完整抓包在 `target/usb-passive-capture.txt`，该目录不纳入版本控制。
拔线后 `4613` 消失；接收器仍插着时程序可重新发现 `1413`。
本次未验证蓝牙、配置读写、USB 控制传输命令或固件升级协议。
